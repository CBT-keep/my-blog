那天，我持以往常学习的CRUD知识，将我的博客以比较青涩的方式完成了，接着我兴致冲冲，把做好的网站就分享到我的社交圈里，没错，这时候的 CBT-keep 还是个内向的 Boy ，来围观 CBT-keep 的人还很少，对网站来说，这点流量对 2C2G 的服务器来说还是可以相当轻松应对的。

不过，随着 CBT-keep 疯狂拓宽他的社交圈，好奇 CBT-keep 生活又或者是他学习过程的人越来越多，他们后来都了解到他的博客，一时间博客的用户越来越多，在某一天，这些用户仿佛约好了一样，一起涌入这个网站，服务器瞬间接收到了大量的服务请求。在程序层面，由于CBT-keep当时能力不足，还不知道什么是Redis，更不知道什么是异步处理，所以对网站服务的请求全部都击打在了数据库上，我们的数据库很快就无力承担这份流量，给CBT-keep发来告警提示...

没错，所以我们在这就是为了讨论这个问题如何解决，我将会以全流程去修复这个问题。

我们知道，MySQL是基于储存的服务，对数据有持久化作用，然而这也意味着我们的服务如果使用MySQL来处理这么大量的请求的话，将会导致我们的请求处理如同当年使用机械硬盘的电脑一样会让人崩溃。因此，为了得到更高的性能，我们就需要换用基于“内存”的数据库服务。

> 但这并不意味着MySQL被替代了，在程序中MySQL的地位依旧不可撼动，起着保证数据最终状态的作用，因为基于内存的数据库在经历异常或者重启时，就会丢失内存中的数据。

因此，我们引入Redis，CBT-keep 的博客当时把所有请求都直接打到 MySQL 上，而 MySQL 是基于磁盘的持久化数据库。每次查询博客文章，都要经历“连接数据库 → 解析 SQL → 磁盘 I/O 读取数据 → 返回结果”这一整套流程。在并发量低的时候，这个过程可能只需要几十毫秒，用户毫无感知。但当大量用户同时涌入，数据库连接池很快就会被占满，磁盘 I/O 成为瓶颈，响应时间从几十毫秒飙升到几秒甚至十几秒，最终数据库直接拒绝服务，博客页面一片空白。

### 旁路缓存（Cache-Aside Pattern）

引入 Redis 之后，博客的读写流程就变成了经典的“旁路缓存模式”，这是业界最常用、最基础的缓存使用方式。

**读操作的流程是这样的：**

当用户请求查看一篇博客文章时，程序不会直接去查 MySQL，而是先去 Redis 里查对应的缓存 Key（比如 `article:1001`）。如果 Redis 里有数据（缓存命中），直接返回，整个过程耗时在微秒级别，MySQL 完全不用参与。如果 Redis 里没有（缓存未命中），再去 MySQL 查询，拿到数据之后顺手把结果写入 Redis，并设置一个合理的过期时间（比如 5 到 30 分钟），这样下次同样的请求就能直接命中缓存了。

**写操作的流程是这样的：**

当你发布新文章、修改文章内容或者删除文章时，流程是**先更新 MySQL，再删除 Redis 中对应的缓存**。注意这里是“删除”而不是“更新”缓存，原因有两个：第一，删除操作比更新操作更轻量；第二，在高并发场景下，如果采用“更新缓存”的方式，可能会出现线程 A 先更新数据库、线程 B 后更新数据库，但线程 B 的缓存更新反而先执行的情况，导致缓存里存的是旧数据。而删除操作是幂等的，不管删多少次，效果都是一样的，不会出现这种并发覆盖的问题。

删除缓存之后，下一次有读请求过来时，发现缓存不存在，自然会从 MySQL 重新加载最新数据并回写到 Redis，这样就保证了数据的最终一致性。

没错，这样听起来似乎很不错，CBT-keep马上动手实践，将部分频繁查询的文章数据加入了缓存，流量高峰问题得到了缓解，但是很快就又遇到了问题...

### 三大经典缓存问题：穿透、击穿、雪崩

#### 缓存穿透：查询不存在的数据

缓存穿透指的是用户不断请求缓存和数据库中都不存在的数据。比如有恶意用户或者爬虫程序，疯狂请求 `article?id=-1` 或者 `article?id=999999` 这种根本不存在的文章 ID。因为数据本身就不存在，所以 Redis 里肯定没有，MySQL 里也没有，每一次请求都会穿透缓存直接打到数据库上。如果有大量这样的请求同时涌入，数据库很快就会被压垮。

解决方案主要有两种：

第一种是**缓存空值**。当从 MySQL 查询结果为空时，不要什么都不做，而是把这个“空结果”也缓存到 Redis 里，比如存一个空字符串或者特殊的标记值，并设置一个较短的过期时间（比如 1 到 5 分钟）。这样当同样的恶意请求再次到来时，Redis 会直接返回空值，不需要再查数据库了。但是CBT-keep转念一想，自己的服务器配置比较低呀，万一要是真的有一些神秘人送来这份大奖怎么办，还不是分分钟给内存占满了。于是CBT-keep继续探索。

第二种是**布隆过滤器**。布隆过滤器是一种空间效率很高的概率型数据结构，可以在请求到达缓存层之前，先判断这个 Key 是否“可能存在”。如果布隆过滤器说“不存在”，那这个数据一定不存在，直接拦截掉，根本不需要去查缓存和数据库。如果布隆过滤器说“可能存在”，才放行去查缓存。布隆过滤器通常会在系统启动时，把数据库中所有有效的文章 ID 加载进去，起到前置拦截的作用。

得到这个解决方案的CBT-keep决定将这两种方案组合使用：先用布隆过滤器拦截掉明显不存在的请求，再配合空值缓存兜底，双重防护。

缓存穿透算是暂时缓解了，接踵而至的是缓存击穿。

#### 缓存击穿：热点 Key 过期瞬间的并发冲击

缓存击穿和缓存穿透不一样，它针对的是**数据库中真实存在、且被高频访问的热点数据**。比如 CBT-keep 的某篇爆款文章，每天有几万人阅读（遐想一下...嘿嘿），这篇文章的缓存 Key 在 Redis 里一直存在。但缓存是有过期时间的，假设这篇文章的缓存刚好在这一刻过期了，而此时此刻恰好有几千个用户同时在请求这篇文章，那么这几千个请求会发现缓存里没有数据，于是全部涌向 MySQL 去查询，数据库瞬间承受巨大压力，甚至直接宕机。

这可不行！CBT-keep开始寻找解决方案：

第一种是**互斥锁（分布式锁）**。当缓存失效时，不是让所有线程都去查数据库，而是只允许一个线程去查库重建缓存，其他线程等待或者返回旧值。具体做法是：发现缓存不存在时，先尝试用 Redis 的 `SETNX` 命令获取一个分布式锁，获取成功的线程去查数据库并回写缓存，获取失败的线程休眠一小段时间后重试，或者直接返回旧的缓存数据（如果有的话）。这样可以保证同一时刻只有一个线程在查数据库，避免了并发冲击。

不过很明显的，这个方案下的性能肯定比较低，毕竟是需要阻塞所有进程的。

第二种是**逻辑过期**。这种方式不设置物理上的过期时间，而是在缓存的 Value 里内嵌一个逻辑过期时间字段。每次读取缓存时，先检查逻辑过期时间是否已过期。如果没过期，直接返回数据；如果已过期，不阻塞当前请求，而是返回旧数据，同时开启一个后台异步线程去重新加载最新数据并更新缓存。这样做的好处是请求不会被阻塞，用户体验更好，但实现起来稍微复杂一些。

第三种是**热点数据永不过期**。对于那些访问频率极高的核心数据，可以干脆不设置过期时间，由后台定时任务主动刷新缓存。这样就不存在“过期瞬间被击穿”的问题了。

好不容易解决了这两个问题后，马上就又出现了新的问题 -- 缓存雪崩。

#### 缓存雪崩：大量 Key 同时过期或 Redis 宕机

缓存雪崩指的是在某一时刻，缓存中的大量 Key 同时过期失效，或者 Redis 服务器直接宕机了，导致所有请求瞬间全部涌向数据库，造成数据库压力骤增甚至崩溃。和缓存击穿不同的是，缓存击穿是“一个热点 Key 过期”，而缓存雪崩是“大批 Key 同时过期”，影响范围更广。

针对“大量 Key 同时过期”导致的雪崩，解决方案是**给每个 Key 的过期时间加上随机抖动值**。比如原本统一设置缓存过期时间为 1 小时，现在改成 `3600 + random(0, 1800)` 秒，也就是 1 小时到 1.5 小时之间随机。这样每个 Key 的失效时间就分散开了，不会出现集体失效的情况。

针对“Redis 宕机”导致的雪崩，解决方案是**构建高可用架构**。比如部署 Redis 主从复制 + 哨兵（Sentinel）机制，主节点负责写请求，从节点分担读请求，当主节点发生故障时，哨兵会自动进行故障转移，把某个从节点提升为主节点，保证服务不中断。如果数据量更大、并发更高，还可以采用 Redis Cluster 集群方案，通过数据分片实现水平扩容。

另外，还可以引入**多级缓存**作为兜底：在应用本地使用 Caffeine 等本地缓存作为第一级，Redis 作为第二级。即使 Redis 挂了，本地缓存还能扛住一部分流量，给系统争取修复时间。

三大经典问题被顺利缓解了，但CBT-keep停下来想了想，原本只需要维护从客户端 -> MySQL的服务，现在变得好复杂，还要什么本地缓存、Redis。太复杂了，会不会出现在这个过程中出现数据不一致问题啊？传递不够彻底？线程并发过程中的争抢行为？因此CBT-keep继续探索。

### 缓存一致性：Redis 和 MySQL 到底谁说了算？

引入缓存之后，一个很现实的问题就摆在了CBT-keep面前：

**MySQL里的数据和Redis里的数据，到底谁才是真的？**

答案其实很明确：

> MySQL才是真正的数据源，Redis只是为了提高读取性能而存在的缓存。

Redis里的数据本质上是MySQL数据的一个“副本”。既然是副本，那就意味着它一定存在和MySQL数据不一致的可能。

比如现在CBT-keep修改了一篇文章：

```text
MySQL：
article:1001
title = "Redis缓存入门"
```

Redis里也缓存了一份：

```text
article:1001
title = "Redis缓存入门"
```

此时CBT-keep把文章修改成：

```text
title = "Redis缓存进阶"
```

如果只更新了MySQL，而忘记删除Redis，那么下一位用户访问文章时：

```text
	用户
 	 ↓
    Redis
 	 ↓
"Redis缓存入门"
```

用户看到的依然是旧数据。这就是最经典的：

**缓存与数据库数据不一致。**

所以我们前面才会强调：

> 写操作：先更新MySQL，再删除Redis缓存

但CBT-keep很快又发现：“如果我先更新MySQL，然后删除Redis的过程中突然服务器宕机了呢？”

比如：

```text
① 更新MySQL成功
② 删除Redis失败
③ 请求结束
```

这时候MySQL已经是新数据：

```text
MySQL → 新数据
Redis  → 旧数据
```

下一次用户访问时，Redis命中旧数据，问题还是出现了。

那是不是可以反过来：

```text
① 删除Redis
② 更新MySQL
```

看起来好像也不错。

但是如果：

```text
① 删除Redis成功
② 更新MySQL失败
```

那么下一次请求就会因为Redis没有数据而去查询MySQL。而MySQL里面还是旧数据。然后这个旧数据又会被重新写入Redis。

于是：

```text
Redis被删除
    ↓
MySQL更新失败
    ↓
查询MySQL旧数据
    ↓
旧数据重新进入Redis
```

CBT-keep看着这个流程，陷入了沉思。好像怎么做，都没有办法通过简单的两步操作做到百分之百的一致。

没错。这时候我们需要接受一个事实：

> 缓存系统通常追求的是最终一致性，而不是强一致性。

只要我们的业务允许短时间的数据延迟，那么就不需要为了追求绝对一致性，把整个系统搞得极其复杂。

### 延迟双删：再给缓存一次机会

不过，CBT-keep还是不太甘心。

“既然我第一次删除Redis的时候可能因为并发或者其他原因出现问题，那我再删一次不就好了？”

于是就出现了一种比较经典的方案：**延迟双删。**

它的流程大概是：

```text
① 删除Redis缓存
② 更新MySQL
③ 等待一小段时间
④ 再次删除Redis缓存
```

为什么要删除两次？因为在高并发场景下，可能存在这样的情况：

```text
线程A：删除Redis
线程B：查询MySQL
线程A：更新MySQL
线程B：把旧数据写入Redis
```

于是Redis里面又重新出现了旧数据。这时候第二次删除就派上用场了：

```text
线程A：再次删除Redis
```

把线程B刚刚写进去的旧数据再删除一次。下一次用户请求进来：

```text
Redis没有数据
    ↓
查询MySQL
    ↓
拿到最新数据
    ↓
写入Redis
```

这样就能进一步降低缓存出现脏数据的时间窗口。当然，CBT-keep也知道：

> 延迟双删不是严格意义上的强一致性方案。

它只是通过再次删除，降低并发场景下缓存与数据库不一致的概率和持续时间。而且这个“延迟多久”本身也是一个需要根据业务情况调整的问题。如果延迟太短，可能无法覆盖前面的并发操作。如果延迟太长，缓存中的旧数据又会存在更久。所以在真实生产环境中，还需要结合业务访问模型、线程执行时间以及数据库压力来进行设计。

### 那如果删除Redis失败怎么办？

CBT-keep继续思考。前面的问题其实还没有完全解决。

假设：

```text
① MySQL更新成功
② Redis删除失败
```

怎么办？总不能让程序发现Redis删除失败之后，就一直重试吧？如果Redis整个挂掉了，程序岂不是卡在那里？

所以我们又需要引入一个非常重要的思想：

> **失败重试。**

例如可以把需要删除的缓存Key记录下来：

```text
article:1001
```

然后通过消息队列、定时任务等方式进行异步重试。

流程就变成：

```text
更新MySQL
   ↓
删除Redis
   ↓
  成功 → 结束
   ↓
  失败
   ↓
记录删除任务
   ↓
 异步重试
   ↓
Redis删除成功
```

这时候，缓存删除就不再完全依赖当前请求。

哪怕当前请求执行过程中Redis暂时出现故障，也可以通过后续的重试机制最终把脏缓存清理掉。

这其实也是分布式系统中非常重要的一个思想：

> 不要指望所有操作一次成功，而是要设计失败之后怎么办。

### 并发更新：两个CBT-keep同时修改一篇文章

解决完缓存一致性，CBT-keep刚准备松一口气，新的问题又出现了。

假设现在有两个请求：

```text
请求A：把文章修改成 "Redis入门"
请求B：把文章修改成 "Redis进阶"
```

两个请求几乎同时到达。

于是：

```text
A：更新MySQL
B：更新MySQL
A：删除Redis
B：删除Redis
```

看起来好像没有什么问题。但是如果我们的缓存更新方式不是“删除”，而是“直接写入缓存”，情况就开始变得有意思了。

比如：

```text
A：MySQL写入 "Redis入门"
B：MySQL写入 "Redis进阶"

B：Redis写入 "Redis进阶"
A：Redis写入 "Redis入门"
```

最终：

```text
MySQL → Redis进阶
Redis  → Redis入门
```

又出现了数据不一致。这就是为什么我们之前一直强调：

> 更新数据库之后，删除缓存，而不是直接更新缓存。

因为缓存只是副本。我们没必要在写操作的时候费尽心思维护一个完整的缓存状态。让缓存失效，然后下一次读取时重新从MySQL加载，反而更加简单可靠。

------

### 缓存重建：又一个并发问题

CBT-keep突然发现：“删除缓存之后重新加载，这个动作本身不会又产生并发问题吗？”

答案是：**会**，比如Redis里的：

```text
article:1001
```

刚刚被删除。此时来了100个请求：

```text
请求1 → Redis Miss
请求2 → Redis Miss
请求3 → Redis Miss
...
请求100 → Redis Miss
```

然后这100个请求全部去查询MySQL。虽然我们解决了缓存击穿，但是如果没有任何控制，这100个请求还是会同时查询数据库。

于是我们又回到了最开始的问题：

```text
Redis缓存失效
    ↓
大量请求同时Miss
    ↓
大量请求查询MySQL
    ↓
MySQL压力增加
```

所以对于缓存重建，我们通常还需要进行**并发控制**。

------

### 分布式锁：让一个人去查数据库就够了

这个时候Redis又站了出来。我们可以使用Redis提供的：

```text
SET key value NX EX
```

来实现一个简单的分布式锁。

比如：

```text
lock:article:1001
```

当线程发现缓存不存在时，先尝试获取这个锁。

```text
线程A → 获取成功
线程B → 获取失败
线程C → 获取失败
线程D → 获取失败
```

那么：

```text
线程A
 ↓
查询MySQL
 ↓
写入Redis
 ↓
释放锁
```

其他线程发现锁已经被释放之后，再重新查询Redis。

于是整个过程就变成：

```text
             Redis
               ↓
          Cache Miss
               ↓
        尝试获取分布式锁
          ↙           ↘
      获取成功       获取失败
         ↓               ↓
      查询MySQL       等待/重试
         ↓               ↓
      写入Redis  ←───────┘
         ↓
      返回数据
```

这样原本可能有1000个请求同时打MySQL，现在只需要一个请求去查询数据库。

这就是分布式锁最常见的应用之一：

> 控制同一资源的并发访问

不过CBT-keep很快又发现：“等等，如果那个拿到锁的线程突然挂了呢？”

比如：

```text
线程A获取锁
    ↓
开始查询MySQL
    ↓
服务器突然宕机
```

如果这个锁没有过期时间，那么：

```text
lock:article:1001
```

可能会永远存在。

后面的线程全部拿不到锁。

所以分布式锁必须考虑：锁的过期时间、锁的唯一标识、释放锁的安全性以及续期问题。

这也是为什么真实生产环境中的分布式锁远远没有：

```text
SETNX
```

这么简单。

------

### Redisson：把分布式锁这件事交给专业工具

CBT-keep研究了一下，发现自己如果手动实现分布式锁，需要考虑的东西实在太多：

```text
锁超时怎么办？
业务执行时间超过锁时间怎么办？
锁被别人误删怎么办？
Redis发生故障怎么办？
线程之间如何安全释放锁？
```

于是他发现了一个非常熟悉的家伙：**Redisson。**

Redisson对Redis进行了进一步封装，提供了更加完整的分布式锁能力。

于是程序中的代码就从原来的：

```text
RedisTemplate
    ↓
  SETNX
    ↓
 EXPIRE
    ↓
   DEL
```

变成了更加接近我们日常使用方式的：

```text
获取锁
    ↓
执行业务
    ↓
释放锁
```

而像锁自动续期、可重入锁等问题，则交给专门的组件去处理。

当然，这并不意味着Redisson就能让分布式锁变成“绝对可靠”。

分布式系统没有那么简单。

我们依然需要根据业务场景考虑锁的粒度、超时时间以及异常处理。

### Redis 原子性：为什么有时候需要 Lua？

CBT-keep研究分布式锁的时候，又发现了一个问题。前面我们使用：

```redis
SET lock:article:1001 unique-value NX EX 30
```

来获取锁。获取锁其实还比较简单，因为 `SET ... NX EX` 可以在一个 Redis 命令中完成。

但是，**释放锁就没有这么简单了**，我们不能直接：

```redis
DEL lock:article:1001
```

因为这个锁有可能已经不是自己的了。例如：

```text
线程A：
获取锁
value = A
    ↓
执行业务
    ↓
业务执行时间超过30秒
    ↓
锁自动过期
```

这时候：

```text
线程B：
发现锁已经过期
    ↓
重新获取锁
value = B
```

但是线程A可能过了一会儿才执行完：

```text
线程A：
业务执行完成
    ↓
DEL lock:article:1001
```

问题就出现了：

```text
线程B：
刚刚获得的锁
    ↓
被线程A删除了！
```

这就是经典的锁误删问题！所以释放锁之前，我们必须先判断：

```text
Redis中的value是不是我自己的？
```

也就是：

```text
GET lock:article:1001
        ↓
判断value == 当前线程唯一标识
        ↓
是
        ↓
DEL lock:article:1001
```

看起来没有问题。但是这里又出现了一个新的问题：

> GET、判断、DEL 是三个步骤

如果把它们分成多个 Redis 命令执行，就无法保证整个过程是原子的。例如：

```text
线程A：

GET lock
 ↓
发现 value = A
 ↓
准备 DEL
```

就在这个时候发生线程切换。假设锁刚好过期：

```text
线程A：
GET → A

        ↓ 锁过期

线程B：
GET → 获取锁
value = B

        ↓

线程A：
DEL lock
```

结果：

```text
线程B的锁
   ↓
被线程A删除
```

所以我们真正需要的是：

```text
判断锁是不是自己的
        +
删除锁
```

这两个操作必须作为一个整体执行。

这时候，Redis Lua 脚本就派上用场了。

------

### Lua：把多个 Redis 操作放进一个原子操作

Redis支持使用Lua脚本在服务器端执行一组Redis命令。例如安全释放分布式锁：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

调用的时候：

```text
KEYS[1]
    ↓
lock:article:1001

ARGV[1]
    ↓
当前线程生成的唯一标识
```

整个过程变成：

```text
Lua脚本
   ↓
GET lock
   ↓
判断value
   ↓
如果是自己的锁
   ↓
  DEL
```

Redis会把整个Lua脚本作为一个整体执行。

也就是说，在脚本执行过程中，其他客户端的命令不会插入到这个脚本的执行过程之间。因此：

```text
GET + 判断 + DEL
```

就可以变成一个原子的业务操作。

这就是Lua脚本在Redis中最经典的应用之一：

> 将多个Redis操作组合成一个不可被其他命令插入的原子执行过程

------

### Redis的“原子性”到底是什么意思？

到了这里，CBT-keep又发现：“Redis不是本来就很快吗？为什么还要专门讨论原子性？”因为快和原子性是两回事

例如：

```redis
INCR counter
```

这是Redis提供的单个命令。Redis会将这个命令作为一个完整操作执行，因此不会出现简单的：

```text
GET
↓
客户端计算
↓
SET
```

这种中间状态被其他Redis命令插入的问题。但是如果我们自己写：

```text
GET counter
    ↓
客户端计算
    ↓
SET counter
```

就可能发生：

```text
线程A：GET → 100
线程B：GET → 100

线程A：SET → 101
线程B：SET → 101
```

最终：

```text
counter = 101
```

而不是我们可能期望的：

```text
counter = 102
```

这就是典型的并发更新问题。所以我们需要理解：

> Redis的单个命令通常具有原子性，但多个命令组合起来，并不会天然成为一个原子操作

例如：

```text
GET
+
判断
+
SET
```

并不等于：

```text
一个原子操作
```

而Lua脚本可以帮助我们把多个Redis操作组合起来。

------

### Lua不仅能用于分布式锁

CBT-keep发现，Lua的用途远远不只是释放分布式锁。

比如一个非常常见的场景：

**秒杀扣库存。**

假设Redis中：

```text
stock:1001 = 10
```

现在来了大量用户抢购。

最简单的想法是：

```text
GET stock
    ↓
判断 stock > 0
    ↓
DECR stock
```

但是这三个步骤如果分开执行，就可能出现并发问题。

所以可以使用Lua：

```lua
local stock = tonumber(redis.call('get', KEYS[1]))

if stock == nil then
    return -1
end

if stock <= 0 then
    return 0
end

redis.call('decr', KEYS[1])

return 1
```

于是：

```text
读取库存
   ↓
判断库存
   ↓
扣减库存
   ↓
返回结果
```

就可以在一次Lua脚本执行过程中完成。调用方只需要根据返回值判断：

```text
1  → 抢购成功

0  → 库存不足

-1 → 商品不存在
```

这样就避免了大量请求在：

```text
读取库存
    ↓
判断库存
    ↓
扣减库存
```

之间互相干扰。

------

### Lua的一个重要特点：执行期间会阻塞其他命令

不过CBT-keep也不能因为Lua很好用，就开始什么都往Lua里面塞。因为Redis执行Lua脚本的时候，脚本本身是一个整体。

也就是说：

```text
Lua脚本执行
    ↓
其他客户端命令需要等待
```

如果Lua脚本里面只有几个简单操作：

```text
GET
判断
DEL
```

执行时间非常短，通常没有问题。

但是如果写了一个非常复杂的脚本：

```text
大量循环
大量计算
大量Redis操作
```

那么：

```text
Lua执行时间过长
        ↓
Redis主线程长时间被占用
        ↓
其他请求等待
        ↓
Redis延迟上升
```

所以Lua的原则应该是：

> **用Lua保证关键操作的原子性，但不要把大量复杂业务逻辑全部塞进Redis。**

Redis应该负责：

```text
高性能数据操作
原子性操作
简单业务判断
```

而复杂业务逻辑仍然应该放在应用程序中。

------

### 从SETNX到Lua：一个完整的分布式锁

现在CBT-keep重新回头看分布式锁，就可以把整个过程串起来了。

#### 获取锁

```redis
SET lock:article:1001 unique-value NX EX 30
```

其中：

```text
lock:article:1001
        ↓
锁的Key

unique-value
        ↓
当前线程唯一标识

NX
        ↓
不存在才能设置

EX 30
        ↓
30秒自动过期
```

获取成功：

```text
线程A
 ↓
获得锁
 ↓
执行业务
```

其他线程：

```text
线程B
 ↓
获取锁失败
 ↓
等待/重试
```

------

#### 释放锁

不能直接：

```redis
DEL lock:article:1001
```

而应该：

```text
判断：
Redis中的value
        ↓
是不是当前线程的unique-value？
        ↓
是
        ↓
删除
```

通过Lua实现：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

于是整个分布式锁就变成：

```text
             SET NX EX
                 ↓
              获取锁
                 ↓
              执行业务
                 ↓
          Lua判断是否自己的锁
                 ↓
            ┌────┴────┐
            ↓         ↓
          是          否
            ↓         ↓
          DEL       不删除
```

这才是一个相对完整的Redis分布式锁基本实现。

当然，真实生产环境还需要继续考虑：

```text
锁续期
锁超时
Redis故障
主从切换
网络分区
业务执行时间超过锁TTL
锁误释放
可重入
公平性
```

所以前面CBT-keep才会发现：

> 自己手写一个真正可靠的分布式锁，比想象中复杂得多

------

### Redis原子操作并不等于“Redis什么都能保证”

到了这里，CBT-keep又必须明确一个概念：

> **Redis的原子性解决的是Redis内部操作之间的并发问题，并不意味着整个分布式系统都自动具有强一致性。**

例如：

```text
MySQL更新
    ↓
Redis更新
```

即使Redis内部的操作是原子的，也不能保证：

```text
MySQL成功
Redis成功
应用成功
消息队列成功
```

这些跨系统操作天然形成一个整体事务。

所以：

```text
Redis原子性
        ≠
分布式事务
```

Redis Lua能解决的是：

```text
Redis内部多个操作
        ↓
原子执行
```

而不是：

```text
MySQL
+
Redis
+
MQ
+
多个服务
```

全部变成一个原子事务。

这两个概念一定要区分开。

### 到这里，Redis的知识链终于完整了

现在CBT-keep再回头看之前遇到的问题：

```text
缓存击穿
    ↓
需要并发控制
    ↓
分布式锁
    ↓
SET NX EX
    ↓
锁的安全释放
    ↓
GET + 判断 + DEL不是一个原子操作
    ↓
Lua脚本
    ↓
Redis原子性
    ↓
Redisson封装
```

于是Redis就不再只是：

```text
GET
SET
DEL
```

这么简单。

我们真正需要掌握的是：

```text
数据结构
    ↓
缓存
    ↓
缓存问题
    ↓
并发控制
    ↓
分布式锁
    ↓
Redis原子性
    ↓
Lua脚本
    ↓
Redisson
    ↓
高并发场景
```

这时候，CBT-keep才真正理解：

> Redis真正难的地方，并不是记住多少个命令，而是理解**多个请求同时到达时，Redis到底能保证什么，不能保证什么，以及如何利用原子操作把关键业务逻辑控制住。**

### 缓存预热：为什么一定要等用户来访问？

解决了缓存一致性和并发问题以后，CBT-keep又开始观察自己的系统。

他发现一个奇怪的事情：

每次Redis重启之后：

```text
Redis：空空如也
```

然后用户一访问：

```text
Redis Miss
 ↓
MySQL
 ↓
Redis
```

如果此时正好是网站刚刚启动，大量用户同时访问热门文章，那不就又产生了一次巨大的缓存重建压力？

所以我们可以提前把热点数据加载到Redis。

这就是：**缓存预热。**

比如系统启动的时候：

```text
查询热门文章
    ↓
写入Redis
    ↓
应用正式接收流量
```

或者通过定时任务：

```text
统计最近访问量
    ↓
找到Top N热点文章
    ↓
提前加载到Redis
```

这样用户第一次访问的时候，Redis里已经有数据了。

请求就可以直接：

```text
用户
 ↓
Redis
 ↓
返回
```

而不是：

```text
用户
 ↓
Redis Miss
 ↓
MySQL
 ↓
Redis
 ↓
返回
```

对于热点数据来说，缓存预热可以有效降低系统刚启动或者流量突然增加时对MySQL造成的压力。

------

### 但是，Redis也不是无限大的

CBT-keep看着自己的Redis：

```text
Redis
├── article:1001
├── article:1002
├── article:1003
├── article:1004
├── article:1005
├── article:1006
└── ...
```

突然意识到一个问题：**“我要是一直往里面塞数据，Redis不会爆吗？”**

当然会。虽然Redis基于内存，速度非常快，但内存毕竟不是无限的。所以我们需要给Redis设置合理的：**最大内存限制**

当Redis达到最大内存之后，就需要根据配置好的淘汰策略删除一部分数据。

比如：

```text
LRU
```

也就是：

> Least Recently Used，最近最少使用

简单来说，就是优先淘汰那些长时间没有被访问的数据。

还有：

```text
LFU
```

也就是：

> Least Frequently Used，最不经常使用

它更加关注一个Key到底被访问了多少次。

除此之外，还有：

```text
allkeys-lru
allkeys-lfu
volatile-lru
volatile-lfu
volatile-ttl
noeviction
```

等等策略。具体选择哪一种，并没有所谓的“万能答案”。需要根据缓存的数据类型、访问模式以及业务特点进行选择。

对于CBT-keep的博客来说，文章数据通常具有明显的热点特征：

```text
少数热门文章
    ↓
大量用户访问

大量冷门文章
    ↓
几乎没人访问
```

那么使用合理的淘汰策略，就可以让有限的内存尽可能服务更多的热点数据。
