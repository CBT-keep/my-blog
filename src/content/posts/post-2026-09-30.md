### 什么是Spring事务？
Spring 事务本质上是对数据库事务的一层封装，它本身不发明事务，而是通过 AOP 代理帮你自动完成“开启事务、提交事务、回滚事务”这些重复操作。

### 它解决什么问题？
比如一个下单流程里，要扣库存、创建订单、扣优惠券。如果中间某一步失败，前面已经执行的操作必须一起回滚，否则数据就会不一致。Spring 事务就是把这一组数据库操作绑定到同一个事务里，要么全部成功，要么全部回滚。

### 核心实现机制
Spring 事务主要依赖三件事：
1. 数据库本身支持事务
例如 MySQL 的 InnoDB 引擎。如果表是 MyISAM，Spring 配得再好也回滚不了。
2. 事务管理器 PlatformTransactionManager
它屏蔽了不同数据源的差异，常见实现有 DataSourceTransactionManager、JpaTransactionManager、JtaTransactionManager 等。
3. AOP 动态代理
Spring 启动时扫描 @Transactional，为 Bean 创建代理对象。调用方法时，代理会先开启事务，执行方法，再根据是否抛异常决定提交或回滚。
简化流程是：
```
调用 @Transactional 方法
  → 进入代理对象
  → TransactionInterceptor 拦截
  → 开启事务 / 加入已有事务
  → 执行业务方法
  → 正常返回则 commit
  → 抛出异常则 rollback
```

### 关键配置点
@Transactional 里比较重要的属性有：
propagation：传播行为，默认 REQUIRED，即有事务就加入，没有就新建。
isolation：隔离级别，默认 DEFAULT，使用数据库默认级别。
rollbackFor：指定哪些异常触发回滚，默认只对 RuntimeException 和 Error 回滚。
timeout：事务超时时间，超时会自动回滚。
readOnly：只读事务，适合纯查询场景，数据库可做优化。

聊完了这些，就来看今天遇到的问题，先说说场景：
在秒杀业务中，创建订单需要进行多次查库，因此，事务机制是不可避免的了，因此，我们构建了这样的一个案例：

```java
synchronized (userId.toString().intern()){
    IVoucherOrderService proxy = (IVoucherOrderService) AopContext.currentProxy();
    return proxy.createVoucherOrder(voucherId);
}
```

createVoucherOder是长这样的：

```java
@Transactional
public Result createVoucherOrder(Long voucherId) {
}
```

在这里为什么我们没有像之前使用一个事务的注解就好了，而是要额外声明一个代理对象，也就是我们案例里面写的 proxy 对象来帮助构建呢？
在学习Spring事务时我们就知道，事务不是万能的，它在一些场景下会失效！这里就是几大实效的场景之一。这是由于Spring事务是基于代理对象去构建的，我们如果直接使用 this 这样的构造方法去实现这个创建订单的方法，那么程序就会绕过Spring事务，导致事务实效，因此我们才会去创建这个代理对象。

另外，对于Spring事务失效还有更多情况，我们后面慢慢来讨论。
